The default configuration rebuilds your document on every request — perfect for local development,
wrong for production. This guide covers the production story: commit the artifact, serve it without
re-analyzing, gate who can see it, and let CI catch breaking changes.

## The shape of a production setup

<Steps>

1. **Generate in CI and commit the artifact.** Docuccino's output is deterministic, so a committed
   `docs/openapi.json` is a reviewable, diffable record of your API.

   ```bash
   php artisan docuccino:export --fail-on=warning
   ```

2. **Serve the committed file, not a fresh build.** Point the viewer at the artifact so no request
   ever triggers analysis:

   ```php
   // config/docuccino.php → documents.default.viewer
   'source' => 'artifact', // re-emits the committed export.path; never re-analyzes
   ```

3. **Gate the viewer route** so only the right people reach it (below).

4. **Diff on every change** to enforce your versioning policy in CI (below).

</Steps>

## Choosing a viewer source

The default `viewer.source` of `generate` rebuilds the document on every request — right for local, wrong
for production. In production, serve pre-built bytes instead: `artifact` re-emits the committed
`export.path` with no analysis at request time, and `cache` serves the `docuccino:cache`-warmed payload
(falling back to `generate` on a cold cache) for high-traffic viewers. The
[viewer guide](/laravel/guides/viewer/#source-modes) has the full source-mode table.

For `cache`, warm it on deploy and clear it when you regenerate:

```bash
php artisan docuccino:cache   # build + store each document's payload
php artisan docuccino:clear   # forget the cached payload
```

Set the store with `cache.store` in your config. See the
[commands reference](/laravel/reference/commands/#docuccinocache).

## Gating the viewer

By default the viewer is reachable only in your `local` environment. To expose it anywhere else, name a
`viewer.gate` ability and define it in a service provider — the gate guards the HTML and `.json` routes,
and you should keep `throttle` in `viewer.middleware` when the spec endpoint is public. The
[viewer guide](/laravel/guides/viewer/#access-control) walks through it step by step; to disable the
runtime viewer entirely for a document, set `viewer.route` to `null`.

## When to regenerate

Regenerate whenever the code that shapes your API changes — new routes, changed validation, new
resources or error handling. The natural home for that is CI: export, then diff the fresh document
against the committed one and enforce your versioning policy.

```bash
php artisan docuccino:diff docs/openapi.json --against=HEAD --enforce
```

<Aside type="tip">
Ship a breaking change without the version bump your [`versioning`](/laravel/reference/configuration/#versioning)
policy requires, and `--enforce` fails the build — so your spec and your version number never drift
apart.
</Aside>

## Multitenant base URLs

If your API is served per tenant on a subdomain, describe it once with a server variable rather than a
server per tenant:

```php
// config/docuccino.php → documents.default.servers
'servers' => [
    ['url' => 'https://{tenant}.example.com', 'variables' => [
        'tenant' => ['default' => 'acme', 'description' => 'Tenant slug'],
    ]],
],
```

The viewer renders the variable as an editable field, and the value flows into try-it-out requests.
Server variables are emitted verbatim — see [`servers`](/laravel/reference/configuration/#servers) in
the configuration reference.
