A schema says what a field *is*. An example says what a real call looks like — and it's the part of
your documentation a reader pastes into their client. Inference fills in example values where the code
states them outright, and synthesizes one for every request property whose
[validation rules pin a value](/laravel/documenting/requests/#examples-come-with-the-rules); everything
else on this page is how you supply the rest, either by writing one or by publishing the ones your
tests already produce.

## On a response

Where inference can't derive an example — and for the payloads you actually want a reader to copy —
[`#[Example]`](/laravel/reference/attributes/#example) pins them. One declaration sets the response's
single `example`; several *named* ones publish a map a viewer offers as a picker, so an endpoint can
show what a settled invoice looks like beside an overdue one.

<Tabs>
	<TabItem label="Your code">
	```php
	#[Response(status: 200, type: InvoiceResource::class, description: 'The invoice')]
	#[Example(name: 'paid', summary: 'A settled invoice', value: ['id' => 42, 'status' => 'paid'])]
	#[Example(name: 'overdue', summary: 'One past its due date', value: ['id' => 43, 'status' => 'overdue'])]
	public function show(Invoice $invoice): InvoiceResource { /* … */ }
	```
	</TabItem>
	<TabItem label="Generated OpenAPI">
	```json
	"content": {
	  "application/json": {
	    "schema": { "$ref": "#/components/schemas/InvoiceResource" },
	    "examples": {
	      "overdue": { "summary": "One past its due date", "value": { "id": 43, "status": "overdue" } },
	      "paid": { "summary": "A settled invoice", "value": { "id": 42, "status": "paid" } }
	    }
	  }
	}
	```
	</TabItem>
</Tabs>

The map is sorted by name, so adding an example never moves the ones already there and a diff shows
only what you changed.

## On a request body or a parameter

A field's `example:` on [`#[BodyParameter]`](/laravel/reference/attributes/#bodyparameter) or
[`#[QueryParameter]`](/laravel/reference/attributes/#queryparameter) illustrates that one field.
`#[Example]` illustrates the whole thing — the request body as a reader would send it, or one
parameter — and several named declarations publish a map here too.

<Tabs>
	<TabItem label="Your code">
	```php
	#[Example(name: 'minimal', summary: 'The two required fields', request: true, value: [
	    'name' => 'Acme Ltd',
	    'currency' => 'GBP',
	])]
	#[Example(name: 'with-terms', request: true, file: 'docs/examples/customer-with-terms.json')]
	#[Example(name: 'second-page', parameter: 'page', value: 2)]
	public function store(StoreCustomerRequest $request): CustomerResource { /* … */ }
	```
	</TabItem>
	<TabItem label="Generated OpenAPI">
	```json
	"requestBody": {
	  "required": true,
	  "content": {
	    "application/json": {
	      "schema": { "type": "object", "properties": { "name": { "type": "string" } } },
	      "examples": {
	        "minimal": {
	          "summary": "The two required fields",
	          "value": { "name": "Acme Ltd", "currency": "GBP" }
	        },
	        "with-terms": { "value": { "name": "Acme Ltd", "currency": "GBP", "net_days": 30 } }
	      }
	    }
	  }
	}
	```
	</TabItem>
</Tabs>

`request: true` targets the request body and `parameter:` names a parameter — path, query, header or
cookie, whichever it turns out to be. The full argument list is in the [attribute
reference](/laravel/reference/attributes/#example).

## What sits above a synthesized example

Request properties come with an example already, derived from their own validation rules and checked
against their own schema before it is published — the
[rules reference](/laravel/documenting/requests/#examples-come-with-the-rules) has the table and the
cases that get nothing. It sits at the bottom of the ladder, so everything on this page displaces it:

| The example on a request property comes from | Which beats |
| --- | --- |
| the rules, synthesized | nothing — it is the floor |
| a `#[RuleSchema(example: …)]` on your own rule class | the synthesized one, wherever that rule applies |
| a `#[BodyParameter(example: …)]` / `#[QueryParameter(example: …)]` | both of the above, for that one property |

An `#[Example]` is a different node — the body or the parameter as a *whole*, not one property — so it
never competes with these. A reader gets both: the payload you curated, and per-field values inside the
schema for the fields it doesn't mention.

Nothing synthesized ever silently replaces something you wrote, and nothing you write is held to the
schema by the synthesis — [contract testing](/laravel/guides/contract-testing/) is what checks an
example you wrote yourself.

## Examples from a file

A realistic payload is a poor fit for an attribute argument. Point `file:` at a `.json`, `.yaml` or
`.yml` file relative to your application root and Docuccino reads it in:

```php
#[Example(name: 'full-cart', file: 'docs/examples/full-cart.json', summary: 'Three lines and a discount')]
public function show(Cart $cart): CartResource { /* … */ }
```

The file joins that endpoint's build dependencies, so editing it regenerates the endpoint — including
when you create a file that wasn't there yet. A file Docuccino can't read raises a diagnostic and the
example is left out; nothing partial is ever published.

<Aside type="tip" title="Three YAML spellings to know about">
YAML can express things JSON cannot. `.nan`, `.inf` and `-.inf` parse but have no JSON form, so a file
holding one is refused with an `example-file.invalid` diagnostic rather than published. An unquoted
`2020-01-01` is a *date* to YAML, so it publishes as a number — write `'2020-01-01'` to keep it a
string. And an **empty mapping** publishes as `[]` rather than `{}`: the YAML reader hands back one
kind of array for both, so `{}` and `[]` in a `.yaml` or `.yml` file are the same value by the time
Docuccino sees them. JSON files have none of the three.
</Aside>

<Aside type="caution" title="Spelling an empty object">
`{}` is a real payload — a free-form map with nothing in it — and it survives being published, but only
from a spelling that can say it. An `@example {}` docblock and a `.json` file holding `{}` both publish
`{}`. The other two spellings cannot: an empty mapping in a `.yaml` or `.yml` file publishes `[]`, as
above, and `#[Example(value: [])]` publishes `[]` too, because PHP has one array literal for both and
the attribute is handed the array itself. When the payload you mean is `{}`, put it in a `.json` file
or write it in a docblock.
</Aside>

## Illustrating something other than the success response

By default an example illustrates the success response — the lowest `2xx` the operation documents — in
that response's first media type. `status:` sends it to another response, and `mediaType:` to another
content type:

```php
#[Response(status: 404, type: ProblemDetails::class, description: 'No such invoice')]
#[Example(name: 'not-found', status: 404, value: ['title' => 'Not Found', 'status' => 404])]
public function show(Invoice $invoice): InvoiceResource { /* … */ }
```

Where that error body is one other endpoints return too, it is
[hoisted into a shared component](/laravel/documenting/errors/#repeated-bodies-become-shared-components),
and your name goes with it: the shared response publishes `not-found` beside the keys generated for
endpoints that illustrated the same body without naming anything. Annotating one endpoint never changes
what another publishes.

## Examples your tests recorded

Your suite produces real payloads all day. Recording them gives your document examples with real data
in them — and the build still executes nothing, because the execution already happened, in your tests.

<Steps>

1. **Say where recordings live**, and commit that directory:

   ```php
   // config/docuccino.php → documents.default
   'examples' => [
       'recordings' => 'docs/recordings',
   ],
   ```

2. **Turn the recorder on** in the same bootstrap you registered the [contract-testing
   macros](/laravel/guides/contract-testing/) in:

   ```php
   \Docuccino\Laravel\Testing\ApiContract::record();
   ```

3. **Run your suite**, then read the diff:

   ```bash
   php artisan test
   git diff docs/recordings
   ```

</Steps>

You get one file per operation, named after its stable `x-docuccino.id` — so renaming a route carries
its recordings with it:

<Tabs>
	<TabItem label="docs/recordings/op-v1-kgfeda3prpqaw73i.json">
	```json
	{
	  "docuccino": "recording/1",
	  "operation": "op:v1:kgfeda3prpqaw73i",
	  "endpoint": "GET /api/invoices/{invoice}",
	  "responses": [
	    {
	      "status": "200",
	      "mediaType": "application/json",
	      "body": { "id": 42, "reference": "INV-2026-0042", "total": 149.5, "status": "paid" }
	    }
	  ]
	}
	```
	</TabItem>
	<TabItem label="What the document publishes">
	```json
	"200": {
	  "description": "OK",
	  "content": {
	    "application/json": {
	      "schema": { "$ref": "#/components/schemas/Invoice" },
	      "example": { "id": 42, "reference": "INV-2026-0042", "total": 149.5, "status": "paid" }
	    }
	  }
	}
	```
	</TabItem>
</Tabs>

### The curating is yours, and it happens in the diff

A suite produces dozens of responses per endpoint, most of them near-duplicates and some of them
carrying real data. So the recorder narrows that down to one candidate per status, media type and
[name](#name-the-scenarios-worth-showing), and then hands it to the only reviewer who can judge
it — you, reading a diff, before the file is committed.

Three rules do the narrowing, and each of them exists so the file is a function of your responses
rather than of the run that produced them:

| Rule | Why |
| --- | --- |
| Only an exchange whose **response was checked and passed** is recorded | A body that contradicts its own schema can never become the illustration of it |
| The published body is the one that **fills in the most of the shape** — then the shorter of two that tie | Reordering your tests never changes what the document shows, and the example a reader copies is the one with the most of the contract in it |
| A committed body is left **byte-identical while its shape is unchanged** | A `created_at`, a UUID or an autoincrement key moves on every run and the structure on none of them, so re-recording an unchanged suite rewrites nothing |

That last one is what keeps your artifact stable. Re-record as often as you like: the file changes when
the *shape* of a response changes, which is a change worth reading, and never because a fixture had a
different id this morning. A response keyed *by* ids is stable on the same terms — a map under
`"0193a1f0-…"` holds one kind of thing rather than a member of that name, so which ids it holds never
moves the shape, while how many of them it holds still does. And because every one of the three reads
the responses alone, several test workers can record one operation at once without any of them having
to know about the others.

<Aside type="tip" title="`--parallel` is fine here">
A recording is one operation's, so workers only have to take turns: each one compares its candidate
against the file under an exclusive lock and writes only if it wins. Because the winner is decided by
the bodies and never by their order, the file you commit is the same however the workers raced for it.
[Contract coverage](/laravel/guides/contract-testing/#report-the-responses-your-suite-never-proved) is
a whole-suite question — which documented responses and webhook deliveries did *nobody* prove — so it
needs no lock and no turns at all: each process writes a log of its own and a command unions them once
the run is over.
</Aside>

### Credentials never reach the file

A response captured from a live request can hold a token, a key, or a customer's details, and a
document is a thing people publish. So the recorder replaces credentials **on the way out**, before
anything is written:

- any string under a member name that means a secret — `password`, `api_key`, `secret`, `token`,
  `remember_token`, `ssn`, `cvv` and the rest of the
  [leakage heuristics](/laravel/reference/configuration/#data-leakage) — including everything nested
  beneath it;
- any string that *is* a recognizable credential whatever it's called: a PEM private key, an AWS key
  id, a GitHub or Slack token, a live Stripe key, a JWT, a URL with a password in it.

Each becomes `"[redacted]"`, and only strings are touched — a `token_count` of `5` stays the integer
`5`, so the example goes on satisfying its own schema. Your own `lint.leakage.patterns` apply here too:
teach Docuccino a sensitive member name once and both the lint and the recorder learn it.

A number *called* a credential — `"cvv": 123`, a numeric card number — is a secret too, and it can't be
replaced without making the example contradict its own schema. So it is reported instead: the build
refuses to publish that body at all and tells you where it is, with the same
`examples.recording-unsafe` warning. Nothing but the name can speak for a number, so there the name has
to *be* one of the heuristics rather than contain one — `token` counts, `token_count` doesn't.

Half of `lint.leakage.allow` applies, and only half. A **JSON pointer** into the response body —
`'/meta/next_page_token'` — publishes that one value, because it is a statement about that value. A bare
**property name** silences the lint and is ignored here: it would exempt every member of that name in
every body, which is the difference between accepting one public value and publishing whatever a live
request happened to return.

The build checks again when it reads the file. A committed body that still looks like it holds a
credential — hand-edited, or caught by a heuristic added since — is **not published at all**, and says
so with an `examples.recording-unsafe` warning naming the pointer (never the value).

### Name the scenarios worth showing

A suite that exercises an empty cart, a full one and a locked one has three payloads worth publishing,
and one unnamed slot to publish them in. Name them at the call site — the test already knows which
scenario it set up:

```php
$this->getJson('/api/carts/1')->assertValidResponse(recordAs: 'empty-cart');
$this->getJson('/api/carts/2')->assertValidResponse(recordAs: 'full-cart');
```

Named recordings publish together as the media type's `examples` map, one entry per name, sorted by
name so adding a scenario never moves another:

```json
"content": {
  "application/json": {
    "schema": { "$ref": "#/components/schemas/Cart" },
    "examples": {
      "empty-cart": { "value": { "items": [], "total": 0 } },
      "full-cart":  { "value": { "items": [{ "sku": "COG-1", "qty": 2 }], "total": 49.5 } }
    }
  }
}
```

A name may hold letters, digits, dots, dashes and underscores — it becomes a key a generated client
reads, so the assertion refuses anything else at the line that wrote it. Naming one scenario for a
status names them all: OpenAPI carries `example` or `examples` and never both, so once a name is in
play the unnamed candidates for that status stop being recorded. Taking a name back out of your tests
is the one change re-recording can't make for you — a recorded name is never deleted on the strength of
a run that might have been a partial one, so delete the file and record it again.

The name is always yours. Docuccino will not derive one from the test's name, because renaming a test
would then rename a published example — a change to your contract that nobody asked for.

### Where a recording sits against everything else

A recorded example sits at the `integration(20)` rung of the
[precedence ladder](/laravel/guides/how-it-works/#3-uir). A recording is evidence — your
application really did answer this — so it beats a shape inference merely derived. But an
`#[Example]` is you choosing what a reader should see, and that is never overruled by a test fixture. A
name you passed at a call site *is* a choice, though, so a named recording can sit beside the examples
you curated:

| You wrote | An unnamed recording | Named recordings |
| --- | --- | --- |
| nothing | publishes as the media type's `example` | publish as an `examples` map of their names |
| a singular `#[Example]` | yours, alone | yours, alone |
| named `#[Example]`s | yours, alone | yours plus the recorded names — yours wins any name you both spell |

A singular example is the one place a recording has nowhere to go: filing it beside yours would mean
inventing a name for *yours*, which is not Docuccino's to choose.

A recording is also only ever an illustration. A status or media type your document doesn't describe
gets no example from one — a recording never adds a response the contract doesn't state.

<Aside type="note" title="Names and shared error responses">
Docuccino collapses an error body repeated across operations into one shared component every route
`$ref`s. A media type carrying an `examples` map can't take part in that, so a named recording on a
4xx or 5xx would quietly drop an *unrelated* route's 404 back inline. Rather than let one route's tests
change another route's document, the body publishes there as the singular `example` and an
`examples.recording-name-unpublished` warning tells you the name went nowhere. Turn
[`representation.errors.components`](/laravel/reference/configuration/#representation) off if you would
rather have the names.
</Aside>

### When recordings go stale

Every build reports what is wrong with the committed directory. Every code below is in the
[diagnostics reference](/laravel/reference/diagnostics/#recorded-examples) too, alongside what to do
about each one.

| Code | Severity | Means |
| --- | --- | --- |
| `examples.recordings-empty` | info | The directory you configured holds no recordings yet |
| `examples.recordings-escapes-base` | warning | The directory you configured isn't inside your application, so it was never read |
| `examples.recording-unreadable` | warning | A file in it isn't a recording Docuccino can read |
| `examples.recording-orphaned` | warning | A recording for an operation this document no longer has — the route was renamed, moved or removed |
| `examples.recording-unsafe` | warning | A committed body still holds what looks like a credential; it wasn't published |
| `examples.recording-name-unpublished` | warning | A recorded name on an error response the document shares as a component; the body publishes without it |

<Aside type="caution" title="An example that doesn't match its schema is a lie">
Inference can't be wrong about a shape it derived; a hand-written example can say anything at all, and
it's the part of a document a reader pastes into their client.
[`assertValidExamples()`](/laravel/guides/contract-testing/#catch-an-example-that-lies) holds every
published example — written or recorded — to the schema beside it, so a shape that moves under an
example fails a test instead of shipping.
</Aside>
