Integrations are how Docuccino understands the packages and conventions you already use. Each one
reads a specific part of your app — Form Requests, API Resources, Eloquent models, query builders,
authentication — and contributes the matching pieces of your documentation.

Mostly, you never switch them on. Each integration activates the moment it's relevant: the Spatie Data
support the moment `spatie/laravel-data` is installed, the Passport support the moment Passport is, and
so on. Anything that builds on Laravel itself — validation, Form Requests, resources, models, enums,
error responses, rate limiting — is always available. The one exception is
[Spatie Laravel Permission](/laravel/packages/laravel-permission/), which is opt-in because permission
names expose your internal authorization structure.

<Aside title="Built with the tools you have">
Every integration on this page is built using the same public extension API that's available to
you — you have access to everything Docuccino used to build itself. Nothing here is privileged: if
an integration can read a package, so can one you write. See
[Writing an integration](/extending/extension-authoring/).
</Aside>

## The integration matrix

Each row links to its detailed page. "Requires" tells you what has to be installed for the
integration to activate; "Config" links the knobs that tune it.

### Request &amp; validation

| Integration | What it documents | Requires | Config |
| --- | --- | --- | --- |
| [Validation rules](/laravel/documenting/requests/) | Laravel's validation DSL turned into schema constraints — types, formats, sizes, presence, and enumerations | Built in — always on | — |
| [Form Requests &amp; inline `validate()`](/laravel/documenting/requests/) | Request bodies and query parameters from a Form Request's `rules()`, or an inline `$request->validate([...])` / `Validator::make(...)` | Built in — always on | — |
| [Spatie Data](/laravel/packages/spatie-data/) | Data classes as reusable schemas, and request bodies from Data-typed action parameters | [`spatie/laravel-data`](https://spatie.be/docs/laravel-data) | — |
| [Laravel Actions](/laravel/packages/laravel-actions/) | Action classes as controllers — the resolved `handle()`/`asController()` signature, a request body from `rules()`, a `403` from `authorize()`, and a response body from `jsonResponse()` | [`lorisleiva/laravel-actions`](https://laravelactions.com) | — |

### Responses, models &amp; schemas

| Integration | What it documents | Requires | Config |
| --- | --- | --- | --- |
| [Response inference](/laravel/documenting/responses/) | Success responses from your action return types — resources, models, enums, `JsonResponse` payloads with status codes, and `204` | Built in — always on | — |
| [API Resources](/laravel/documenting/schemas/) | Response schemas from `JsonResource` shapes — plus Laravel's first-party JSON:API resources | `JsonResource` built in; JSON:API auto-activates on Laravel 13 | [`integrations.api_resources.wrap`](/laravel/reference/configuration/#integrations) |
| [JSON:API resources (timacdonald)](/laravel/packages/timacdonald-json-api/) | Pre-13 JSON:API documents from `timacdonald/json-api` resources — identical output to the first-party support, plus `include` / `fields[TYPE]` | [`timacdonald/json-api`](https://github.com/timacdonald/json-api) | — |
| [Eloquent models](/laravel/documenting/schemas/) | Model schemas from columns, refined by `$visible` / `$hidden` / `$appends` / casts — including polymorphic `MorphTo` as a discriminated `oneOf` | Built in — always on | — |
| [Enums](/laravel/documenting/schemas/) | Backed enums by their backing values, `#[CaseDescription]` prose as `x-enumDescriptions`, and optional codegen name hints | Built in — always on | [`representation.enums.naming`](/laravel/reference/configuration/#representation) |

### Error responses

| Integration | What it documents | Requires | Config |
| --- | --- | --- | --- |

## How contributions combine

Several sources can describe the same operation — an inferred type, an integration, a docblock, an
attribute. Docuccino merges them with a clear order of precedence, and higher layers win field by
field (an attribute can override one field of a response without discarding the rest):

```
fallback  <  inference  <  integration  <  docblock  <  attribute  <  overlay  <  config
```

So an integration's best guess is always something you can refine with a docblock or an
[attribute](/laravel/reference/attributes/) — you're never fighting the tool.

Every contribution is recorded with its source in the document's provenance (visible in the raw
[UIR](/uir/)), labeled by the integration that made it — for example `integration:query-builder` or
`integration:sanctum`. That's what lets tooling explain *why* a given detail is documented the way
it is.
