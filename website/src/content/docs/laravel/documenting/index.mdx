Integrations are how Docuccino understands the packages and conventions you already use. Each one
reads a specific part of your app — form requests, API resources, Eloquent models, query builders,
authentication — and contributes the matching pieces of your documentation.

This section is organized by what you're documenting. Start with the page for the concern in front
of you; come back to the matrix below when you want to know whether a particular package is
supported.

## How support activates

Mostly, you never switch anything on:

- **Laravel's own conventions are always available** — validation, form requests, response inference,
  API resources, Eloquent models, enums, error handling, rate limiting. There's no package to detect.
- **A package-backed integration activates the moment its package is installed.** The Spatie Data
  support the moment `spatie/laravel-data` is there, the Passport support the moment Passport is.
- **Everything installed is enabled by default, with one exception.**
  [Spatie Laravel Permission](/laravel/packages/laravel-permission/) is opt-in, because documenting
  role and permission names publishes your app's internal authorization taxonomy.
- **A disabled integration says so.** An integration that's installed but switched off emits one
  `integration.disabled` info diagnostic per build, so the switch is always discoverable from the
  output rather than something you have to remember.

<Aside title="Built with the tools you have">
Every integration on this page is built using the same public extension API that's available to
you — you have access to everything Docuccino used to build itself. Nothing here is privileged: if
an integration can read a package, so can one you write. See
[Writing an integration](/extending/extension-authoring/).
</Aside>

## The integration matrix

Each row links to the page that covers it. **Requires** is what has to be installed for the
integration to activate; **Config** is the bag that tunes it. Anything with an `integrations.*` bag
can also be switched off per document with `integrations.<key>.enabled = false` — see
[`integrations`](/laravel/reference/configuration/#integrations).

### Requests &amp; validation

| Integration | What it documents | Requires | Config |
| --- | --- | --- | --- |
| [Validation rules](/laravel/documenting/requests/) | Laravel's validation DSL turned into schema constraints — types, formats, sizes, presence, and enumerations | Built in — always on | — |
| [Form requests &amp; inline `validate()`](/laravel/documenting/requests/) | Request bodies and query parameters from a form request's `rules()`, or an inline `$request->validate([...])` / `Validator::make(...)` | Built in — always on | — |
| [Spatie Data](/laravel/packages/spatie-data/) | Data classes as reusable schemas, and request bodies from Data-typed action parameters | [`spatie/laravel-data`](https://spatie.be/docs/laravel-data) | [`integrations.spatie_data`](/laravel/reference/configuration/#integrations) |
| [Laravel Actions](/laravel/packages/laravel-actions/) | Action classes as controllers — the resolved `handle()`/`asController()` signature, a request body from `rules()`, a `403` from `authorize()`, and a response body from `jsonResponse()` | [`lorisleiva/laravel-actions`](https://laravelactions.com) | [`integrations.laravel_actions`](/laravel/reference/configuration/#integrations) |

### Responses, models &amp; schemas

| Integration | What it documents | Requires | Config |
| --- | --- | --- | --- |
| [Response inference](/laravel/documenting/responses/) | Success responses from your action return types — resources, models, enums, `JsonResponse` payloads with status codes, rendered views as `text/html`, file downloads and streams, and `204` | Built in — always on | — |
| [API resources](/laravel/documenting/schemas/#api-resources) | Response schemas from `JsonResource` shapes, wrapped per the resource's own `$wrap` | Built in | [`integrations.api_resources.wrap`](/laravel/reference/configuration/#integrations) |
| [First-party JSON:API resources](/laravel/packages/timacdonald-json-api/#which-one-runs) | JSON:API documents from Laravel's own `JsonApiResource`, plus its `include` / `fields[TYPE]` parameters | Laravel 13+ — activates when the `JsonApiResource` class exists | [`integrations.api_resources`](/laravel/reference/configuration/#integrations) |
| [JSON:API resources (timacdonald)](/laravel/packages/timacdonald-json-api/) | Pre-13 JSON:API documents from `timacdonald/json-api` resources — identical output to the first-party support, plus `include` / `fields[TYPE]` | [`timacdonald/json-api`](https://github.com/timacdonald/json-api) | [`integrations.timacdonald_json_api`](/laravel/reference/configuration/#integrations) |
| [Eloquent models](/laravel/documenting/schemas/) | Model schemas from columns, refined by `$visible` / `$hidden` / `$appends` / casts — including polymorphic `MorphTo` as a discriminated `oneOf` | Built in | [`integrations.eloquent`](/laravel/reference/configuration/#integrations) |

## How contributions combine

Several sources can describe the same operation — an inferred type, an integration, a docblock, an
attribute. Docuccino merges them with a clear order of precedence, and higher layers win field by
field (an attribute can override one field of a response without discarding the rest):

```
fallback  <  inference  <  integration  <  docblock  <  attribute  <  overlay  <  config
```

So an integration's best guess is always something you can refine with a docblock or an
[attribute](/laravel/reference/attributes/) — you're never fighting the tool.
[How it works](/laravel/guides/how-it-works/#3-uir) takes the ladder a rung at a time, with what
typically arrives at each one.

Every contribution is recorded with its source in the document's provenance (visible in the raw
[UIR](/uir/)), labeled by the integration that made it — for example `integration:query-builder` or
`integration:sanctum`. That's what lets tooling explain *why* a given detail is documented the way
it is.
