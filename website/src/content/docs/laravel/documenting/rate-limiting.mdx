Any route with Laravel's `throttle` middleware is documented with a `429 Too Many Requests` response
and the accompanying `Retry-After` and `X-RateLimit-*` headers. This is on by default — no package or
configuration required.

## What it documents

Every throttle form Laravel accepts is recognized, and every one of them produces the same `429`:

| Middleware | Recognized |
| --- | --- |
| `throttle:60,1`, `throttle:60`, `throttle:60,0.5` | ✓ |
| `throttle` (bare, no arguments) | ✓ |
| `throttle:10\|60` (guest\|authenticated) | ✓ |
| `throttle:api` (a named limiter) | ✓ — and its `RateLimiter::for` closure is read, see [Named limiters](#named-limiters) |
| `ThrottleRequests::using('api')` / `::with(...)`, including the FQCN strings they render to | ✓ |
| `ThrottleRequestsWithRedis` (the Redis variant) | ✓ |

When a route stacks **several** throttle middlewares, a single `429` is documented from the first, with
a `rate-limit.multiple-throttles` info diagnostic noting the others are enforced independently but not
separately represented.

## Headers describe meaning, not numbers

Every header is documented by what it *means* — no `example`, no allowance baked into the description,
whatever the route throttles at. That's deliberate:

- **A number in the spec goes stale silently.** Nothing fails when somebody edits `throttle:60,1` to
  `throttle:120,1` and the published spec keeps saying 60.
- **It duplicates your own prose.** Your API's docs are where a reader looks for "100 requests a minute
  on the free plan" — with the tiers and the exceptions that go with it, which a single `example` can
  never carry.
- **It churns the document.** Baked-in numbers make a rate-limit tweak rewrite bytes across every
  operation that route touches, so [`docuccino:diff`](/laravel/reference/commands/#docuccinodiff)
  reports a change on operations whose contract did not move.
- **The live headers are authoritative anyway.** A client reads the real limit, the real remaining
  count and the real reset time from its very first response, and a generated SDK reads them from the
  same place.

The payoff is a smaller, calmer document. Because every `429` is byte-identical, all of your throttled
routes [share one `Error429` component](/laravel/documenting/errors/#repeated-bodies-become-shared-components)
instead of an `Error429`, `Error429_2`, `Error429_3` … one per distinct limit.

If your published spec genuinely needs a documented number, state it yourself with an
[Overlay](/laravel/guides/customizing-output/#openapi-overlays-in-practice) — a deliberate claim you
maintain and review, rather than a build artifact that drifts.

## The body follows your error style

Middleware synthesizes the `429`, so no `throw` announces it — Docuccino asks the
[error-response chain](/laravel/documenting/errors/) about `ThrottleRequestsException` anyway, and the body
matches the rest of the document:

| `error_responses` | The `429` body |
| --- | --- |
| `default` | Laravel's `{ "message": string }`, which is what `ThrottleRequests` returns. |
| `problem-details` | The same `ProblemDetails` shape as every other error, under `application/problem+json`. |
| Your own handler covers throttling | Whatever that handler builds. |
| `none`, or nothing in the chain answers | The stock `{ "message": string }`. |

The body is copied in rather than `$ref`'d, because the chain's own shared response carries none of the
`X-RateLimit-*` headers this `429` needs. The finished response — headers and all — is then
[hoisted like any other error response](/laravel/documenting/errors/#repeated-bodies-become-shared-components),
which it can be, because every throttled route states it identically.

## Named limiters

A named limiter (`throttle:api`) registers its rate inside a closure — `RateLimiter::for('api', fn () => ...)`.
Docuccino never *executes* that closure, but it does read it, to tell a limiter it understands from one
it doesn't:

```php
// A limiter Docuccino reads cleanly — no diagnostic.
RateLimiter::for('api', fn (Request $request) => Limit::perMinute(60)->by($request->user()?->id ?: $request->ip()));
```

All of `Limit::perSecond`, `perMinute`, `perMinutes`, `perHour` and `perDay` are recognized, and a
trailing `->by(...)` partition key is ignored — it changes who the limit applies to, not what the limit
is.

A `rate-limit.dynamic-limit` info diagnostic names any limiter Docuccino can't read statically. That
covers a limiter that:

- returns different limits down different branches (a conditional or multi-`return` closure);
- computes its rate from a non-literal value (`Limit::perMinute($request->user()->rate)`);
- is unlimited (`Limit::none()`) or returns an array of limits;
- attaches a custom response body (`->response(...)`).

The same diagnostic fires — naming the limiter — when a route throttles on a name that has no
`RateLimiter::for` registration at all, which is a genuinely useful thing to find out at build time.

The `429` itself is the same either way: what a limiter looks like never changes what the response
documents.

## Configuration

The integration is always on, and has one switch:

```php
// config/docuccino.php → documents.default.integrations
'rate_limit' => ['enabled' => false], // stop documenting 429s in this document
```

Turning it off for a document emits one `integration.disabled` info diagnostic per build, so the choice
stays visible in the output rather than looking like a bug. See the
[`integrations` reference](/laravel/reference/configuration/#integrations).
