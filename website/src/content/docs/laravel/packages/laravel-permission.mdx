Documents the `role:`, `permission:`, and `role_or_permission:` middleware from
[`spatie/laravel-permission`](https://spatie.be/docs/laravel-permission) — the authorization your routes
require, surfaced in the spec.

## Opt-in — off by default

Unlike every other integration, this one is **off by default, even when the package is installed**.
Role and permission names are your application's internal authorization taxonomy; documenting them
publishes that structure into your public API spec. So enabling it is a deliberate choice, made per
document:

```php
// config/docuccino.php → documents.default.integrations
'permission' => ['enabled' => true],
```

When the package is installed but the integration is left off, the build emits a single
`integration.disabled` info diagnostic per document pointing you at the switch — so the opt-in is
discoverable without publishing anything.

:::note
[Sanctum](/laravel/documenting/authentication/) and [Passport](/laravel/documenting/authentication/)
stay on by default: token schemes and OAuth scopes *are* the public contract, so they leak nothing
internal. Only permission names do — which is why this one flips.
:::

## What it documents

Once enabled, a route's permission middleware is documented two ways:

- a machine-readable **`x-permissions`** extension member on the operation, and
- a human-readable line appended to the operation's description — for example,
  *"Requires permission: invoices.view"*.

<Tabs>
	<TabItem label="Your code">
	```php
	// routes/api.php
	Route::get('/invoices', [InvoiceController::class, 'index'])
	    ->middleware('permission:invoices.view');
	```
	</TabItem>
	<TabItem label="Generated OpenAPI">
	```json
	"get": {
	  "description": "Requires permission: invoices.view",
	  "x-permissions": [
	    { "type": "permission", "values": ["invoices.view"] }
	  ]
	}
	```
	</TabItem>
</Tabs>

With the integration enabled, this documents the operation with the structured `x-permissions` member
and the matching description line.

A pipe-separated list is **any-of** — the caller needs any one of the listed roles/permissions, not
all of them — so the description says so explicitly. `permission:invoices.view|invoices.manage`
becomes *"Requires any of these permissions: invoices.view, invoices.manage"*, and the `::using()`
FQCN forms (`PermissionMiddleware::using(...)`) are recognized the same as the short aliases.

An optional guard suffix (`permission:invoices.view,web`) is captured too: the guard name is carried on
the `x-permissions` entry as a `guard` member, so a requirement scoped to a specific auth guard stays
unambiguous.

## Configuration

| Option | Default | Effect |
| --- | --- | --- |
| `enabled` | `false` | Opt in to document `role:` / `permission:` / `role_or_permission:` requirements. Off by default so authorization names aren't published unintentionally. |

Beyond `enabled`, this integration has no options. It's a no-op when the package isn't installed, or
when a route carries no matching middleware. See the
[configuration reference](/laravel/reference/configuration/#integrations) for the full `integrations`
table.
